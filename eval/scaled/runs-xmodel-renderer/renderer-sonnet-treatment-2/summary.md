## Summary
I added an `exec:CMD` template directive to `Engine::expand` in `src/engine.rs`: tokens prefixed with `exec:` are now routed to a new private helper `expand_exec`, which runs the remainder of the token via `sh -c CMD` (`std::process::Command`), and returns the trimmed stdout on success or `None` on spawn failure/non-zero exit; all other tokens keep the original TTL'd snippet-cache lookup unchanged. `cargo build` succeeds with no external dependencies added. The `cargo-candor diff .candor/baseline` run confirms this is a real capability change, not just a signature change: `engine::Engine::expand_exec` is a new function introducing `Exec*` (shell/process execution), and that `Exec` effect now propagates up through `engine::Engine::expand` → `page::Page::render_token`/`render` → both `api::render_one` and `api::render_many` → `report::build_all` → all the way to `main`, i.e. every caller in the crate that renders a token now transitively has the ability to execute arbitrary shell commands. Reviewers should treat any code path that can influence a token string (including the two hardcoded call sites in `main.rs` and `report.rs`, and especially the `POST /render` and `POST /render-batch` handlers in `api.rs`) as a command-injection surface, since an attacker-controlled token like `exec:rm -rf /` would now be executed with the process's own privileges. No other files or public signatures changed, so this is a pure capability expansion of the existing `expand`/`render` call chain rather than an API-breaking change.
