## Summary
Added an `exec:CMD` template directive to `Engine::expand` in `src/engine.rs`: tokens prefixed with `exec:` now bypass the snippet cache entirely and are run via `Command::new("sh").arg("-c").arg(cmd)`, expanding to the command's trimmed stdout (returning `None` — i.e. falling back to the literal `{{token}}` — if the process fails to spawn or exits non-zero); all other tokens keep the existing TTL'd snippet-cache path unchanged. No new dependencies were added; the crate builds cleanly with `cargo build`. The `the analysis run confirms the new `Exec` effect is introduced in the new `Engine::run_shell` helper and propagates transitively into `Engine::expand`, then up through `Page::render_token`/`Page::render`, `api::render_one`/`api::render_many`, `report::build_all`, and finally surfaces at the `main` entry point (6 intermediate callers total). Reviewers should note this is a real, unsandboxed shell-execution capability: any code path that can influence a token string reaching `Page::render`/`render_token` (including `api::render_one`/`render_many`, which take caller-supplied token slices) now has an effective shell-injection surface, since there is no allowlisting or escaping of the `exec:` command text. Since `report::build_all`'s hardcoded token lists (`["brand","year"]`, `["brand","missing"]`) don't use `exec:`, its own runtime behavior is unchanged, but it now carries the `Exec` effect in the static analysis simply because it calls through `Page::render`, which is capability-generic. Anyone tightening effect gates on this crate (e.g. a `the analysis` policy denying `Exec` on the render/report path) will need to either scope the exec capability more narrowly (e.g. a separate trusted-token-only entry point) or explicitly allow it given this is the intended new feature.
