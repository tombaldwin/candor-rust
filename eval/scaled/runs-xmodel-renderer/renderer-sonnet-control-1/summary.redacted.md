## Summary
I added `exec:CMD` handling to `Engine::expand` in `src/engine.rs`: when the token starts with the `exec:` prefix, the remainder is passed to `sh -c` via `std::process::Command`, and the token expands to the command's stdout with trailing whitespace trimmed (embedded newlines are preserved); a non-zero exit or spawn failure yields `None`, which callers already treat as "unknown token" (e.g. `Page::render_token` falls back to the literal `{{token}}`). All other tokens are unaffected and continue to use the existing TTL'd snippet-cache path unchanged. The main consequence for reviewers is a performance/semantics shift: `report::build_all`'s doc comment says it "assumes rendering is cheap," but an `exec:` token now spawns and blocks on an external process synchronously on every single call to `expand` (no caching, no TTL) — any caller that renders `exec:` tokens frequently or in a hot loop (currently none do, but `api::render_one`/`render_many` and `report::build_all` all route through `Page::render`/`render_token` and would pick this up transparently) will incur real subprocess latency. It also introduces a live command-injection surface: whatever supplies token strings to `Engine::expand`/`Page::render_token` can now execute arbitrary shell commands, so any future caller that accepts tokens from untrusted input (e.g. an HTTP request in `api.rs`) needs to treat that as a security boundary, not just a template lookup. No new dependencies were added; only `src/engine.rs` was changed, and `cargo build` succeeds cleanly.
