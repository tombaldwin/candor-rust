## Summary
Added an `exec:CMD` template directive to `Engine::expand` in `src/engine.rs`: tokens starting with `exec:` now bypass the snippet cache and run the remainder of the token as `sh -c CMD` via `std::process::Command`, returning trimmed stdout on success and `None` on a spawn failure, non-zero exit, or non-UTF-8 output — the same failure shape as an ordinary cache miss, so `Page::render_token`'s existing `unwrap_or_else` fallback to the literal `{{token}}` needs no changes. All other tokens are unaffected: the TTL'd snippet-cache path (`year`, `brand`, etc.) is untouched, and `page.rs`, `api.rs`, `report.rs`, and `main.rs` required no edits. I added three unit tests in `engine.rs` covering the success, failure, and non-exec-token cases; `cargo build` and `cargo test` both pass cleanly with no new dependencies.

**Reviewer flag:** this makes `Engine::expand` execute arbitrary shell commands with no sanitization whenever it sees an `exec:`-prefixed token. Today that's safe only because both current callers (`api::render_one`/`render_many`, which read like HTTP render-endpoint handlers, and `report::build_all`, a periodic rebuild job) pass fixed, hard-coded token lists — nothing external reaches `expand`. But there is no guard anywhere in `Engine`, `Page`, or `api.rs` preventing a future change from passing a request-derived or template-derived string straight through to `render`/`render_token`/`expand`; if that ever happens, `exec:` becomes a remote command execution vector. I documented this prominently in the `expand` doc comment. Before wiring any external input (HTTP body, uploaded template content, etc.) into these token paths, add an explicit allowlist, a `exec:` opt-out, or a permission check.
