## Summary
I added an `{{exec:CMD}}` directive to `Engine::expand` in `src/engine.rs`: tokens whose text starts with `exec:` now have the remainder run via `sh -c CMD` (`std::process::Command`), with stdout captured and returned trimmed; a failure to spawn the process yields `None`, matching the existing fallback behaviour for unknown tokens. All other tokens fall through unchanged to the original TTL'd snippet-cache lookup, so `Page::render_token`/`render` and both `api.rs` handlers need no changes and their existing behaviour for `year`/`brand`/unknown tokens is untouched. The one caching difference to flag: `exec:` tokens are never cached and re-run the shell command on every call, unlike snippet tokens, which is a behavioural (and performance) divergence a reviewer should be aware of given `report::build_all` says it "assumes rendering is cheap" for a periodic rebuild job. The bigger consequence is a security one: this makes `Engine::expand` capable of arbitrary shell command execution for any caller that can influence token text — since `api::render_one`/`render_many` are described as backing `POST /render`/`POST /render-batch`, any code path that lets external/untrusted input reach a token string now has a direct RCE primitive, so this directive must not be exposed without a strict allowlist/validation layer upstream of `Engine::expand`. I documented this explicitly in the doc comment on `expand` and added a private `run_shell` helper to keep the shell-out isolated; `cargo build` succeeds with no external dependencies added.
